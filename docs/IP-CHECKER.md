# Проверка доступности и возможной блокировки VPS

Откройте **Диагностика → Доступность VPS-сервера** и введите публичный IP. Доступ к VPS, домен и параметры VPN не требуются. Enter возвращает назад. Кнопка D и экран дополнительных логов удалены. Доступность адреса, порты без ответа и длительность проверки показаны отдельно.

## Как выполняется проверка

| Этап | Что проверяется |
|---|---|
| Подготовка | Публичный адрес, маршрут с диагностической меткой, маршрут с исходным адресом, `ip rule`, интерфейс, доступные правила iptables/nftables |
| Основные пробы | TCP 22, 80, 443, 8080, 8443; ICMP Echo; контрольные TCP/443 разных сетей |
| Уточнение | При необходимости TCP 2053, 2083, 2087, 2096, 2098, 31618; повторные попытки; ICMP нескольких размеров и DF/MTU |
| UDP | QUIC Version Negotiation на 443; при неоднозначном результате — ограниченные DNS/53 и NTP/123 с проверкой идентификаторов ответа |
| Внешнее сравнение | По умолчанию всегда ICMP, TCP/443 и TCP/22 (SSH) с независимых узлов Check-Host; резервный Globalping |
| Протоколы и путь | SSH-приветствие; HTTP; TLS 1.2/1.3 без SNI; HTTPS с проверкой сертификата; SYN-проба при отсутствии TCP Connect; ICMP/UDP/TCP-трассировки |
| Итог | Доступность, возможная причина, уверенность, фактические основания и ограничения; JSON-отчёт |

Резервные стандартные порты проверяются, если основные не ответили. Найденные в InternetDB дополнительные порты могут проверяться и при работающем основном сервисе. Пропущенные пробы обозначаются явно. Обычный лимит — **120 секунд**, не более **трёх одновременно выполняющихся заданий**, трассировка — максимум **15 хопов**. Внешний этап ограничен 35 секундами. Таймауты и отмена завершают сетевые задачи и удаляют временные исключения.

## Дополнительные методы

| Метод | Когда выполняется | Как используется результат |
|---|---|---|
| InternetDB | При разрешённых внешних запросах | До пяти ранее замеченных портов проверяются живым TCP Connect. Общий предел — 18 TCP-портов. Один дополнительный порт сравнивается с внешними узлами вместе с обязательными 443/22 |
| Пассивное приветствие сервиса | До двух найденных открытых дополнительных портов | Читается короткий баннер SSH/SMTP/FTP/HTTP; команды и данные авторизации не отправляются |
| STUN Binding / UDP 3478 | Если основные TCP-сервисы не ответили или 3478 найден в базе | Проверяются тип сообщения, cookie, transaction ID, длина, атрибуты и fingerprint при его наличии. Сопоставленный ответ подтверждает доступность UDP-сервиса; молчание не подтверждает бан |
| ICMP Timestamp | IPv4, если нет Echo Reply и открытых основных TCP-портов | Две ограниченные пробы другого типа ICMP. Ответ принимается только от нужного IP с совпавшими идентификатором, последовательностью, исходным временем и checksum |
| BGP RIS | При найденном префиксе и доступном внешнем API | Показываются число наблюдающих маршрут пиров и время снимка. Снимок старше суток или без подтверждённого времени считается устаревшим |
| RPKI | Для текущего префикса и не более двух origin ASN | `VALID` — ROA соответствует, `INVALID` — требуется проверка маршрутизации, `UNKNOWN` — ROA не найден; это нейтральный результат |
| Локальный firewall | Перед сетевыми пробами | Читаются INPUT/OUTPUT и связанные цепочки таблицы filter. Потенциальный DROP/REJECT, неполный аудит и правила с неоднозначным применением препятствуют уверенному выводу о внешней фильтрации |
| Повторная локальная проба | Если тот же порт ответил с внешних узлов | До трёх дополнительных попыток с паузами. История существует только в памяти текущего запуска |

[InternetDB](https://book.shodan.io/developer-apis/internetdb/) содержит исторические наблюдения: время запроса не является временем последнего сканирования. Его список портов не задаёт транспорт каждого наблюдения; Xmenu проверяет выбранные кандидаты по TCP заново. Отсутствующая запись и недоступный API не означают недоступность VPS.

[RIPE routing-status](https://stat.ripe.net/docs/data-api/api-endpoints/routing-status) показывает наблюдения BGP, а [RPKI validation](https://stat.ripe.net/docs/data-api/api-endpoints/rpki-validation) — соответствие анонса ROA. Эти данные объясняют возможную проблему маршрутизации и не заменяют живой ответ сервера. Ошибка API не превращается в сетевой результат.

Отклонения TLS фиксируются по этапу: например, RST после TCP Connect/ClientHello. Источник RST без дополнительных данных не устанавливается. Сырые TCP-сигнатуры не используются для заявления о конкретном устройстве фильтрации.

## Как читать итог

| Состояние JSON | Значение |
|---|---|
| `REACHABLE` | Получен прямой ответ; полная недоступность IP не подтверждается |
| `PORT_FILTERED` | IP доступен, часть проверенных портов повторно не отвечает. Отсутствующий сервис и источник фильтрации не различимы |
| `LIKELY_PATH_SPECIFIC_FILTERING` | Один IP/порт открыт в двух разных странах/ASN, повторно не отвечает локально, два контрольных подключения работают, прямой маршрут подтверждён; аудит filter не выявил потенциального локального запрета |
| `POSSIBLE_BLOCK` | Есть признаки ограничения пути, но недостаточно независимых подтверждений |
| `LOCAL_NETWORK_PROBLEM` | Нет маршрута или не работают контрольные подключения |
| `CHECK_ERROR` | Необходимые сетевые проверки завершились технической ошибкой |
| `INCONCLUSIVE` | Данных недостаточно; например, все проверенные сервисы молчат или пришли только отказы |

Состояние порта хранится отдельно (`OPEN`, `CLOSED`, `FILTERED`, `OPEN_FILTERED`, `UNKNOWN`, `ERROR`). Timeout не означает доказанный бан. TCP RST может сформировать закрытый порт или промежуточное устройство. UDP без ответа означает неопределённость между отсутствующим сервисом и фильтрацией. Уверенность — `High`, `Medium` или `Low`, без некалиброванных процентов.

Без доступа к серверу невозможно достоверно отличить firewall VPS с ограничением по исходному адресу от фильтрации провайдера. TLS без SNI может отвергаться самим сервером; ошибки сертификата или отказ TLS не доказывают DPI. Проверка handshake без проверки сертификата используется только для определения доступности TLS. HTTPS и внешние API проверяют сертификаты.

## Прямой маршрут

Сокеты используют поддерживаемую правилами метку обхода XKeen/nfqws и привязку к проверенному WAN-интерфейсу. При необходимости добавляются только временные исключения для точной входящей TCP/UDP-пробы: IP, протокол, исходный и локальный порты. Службы не отключаются, маршруты и постоянные правила не меняются. При отмене выполняется rollback, при следующем запуске удаляются найденные исключения завершившихся процессов.

Исходный адрес реальных успешных TCP-соединений сверяется с маршрутом и сохраняется в `path.observed_sources`. Адрес WAN из CGNAT/RFC1918 допустим: NAT провайдера не делает проверку публичного адреса VPS некорректной.

Если правила нельзя прочитать, найден нераспознанный перехват, nftables меняет направление трафика, маршрут проходит через туннель или тип WAN не подтверждён, выводится **`DIRECT_PATH_UNVERIFIED`**. В таком состоянии успешный тест не объявляется доказательством прямой доступности. Необычные PPP/VPN-схемы требуют дополнительной проверки оператором; движок предпочитает неопределённость ложному подтверждению. Проверка отражает снимок правил; изменение маршрутизации во время запуска не поддерживается.

## Приватность и отчёт

При обычном запуске внешние проверки выполняются автоматически, отдельного переключателя в меню нет. Проверяемый IP передаётся Check-Host, при необходимости Globalping, RIPEstat и Shodan InternetDB. Аргумент командной строки `--no-external` позволяет явно выполнить отдельную локальную проверку без запросов к этим API. Старый файл настройки включения/выключения больше не используется.

Результаты и подробности выводятся только на экран; файлы отчётов не создаются. `--json` выводит данные в stdout. Токены, пароли и VPN-конфигурации не читаются.

```sh
xmenu server-check 1.1.1.1 --no-external
```

```sh
xmenu server-check 1.1.1.1 --json --timeout 60
```

Параметры командной строки `--ports` и `--sni` сохранены для совместимости; для обычного запуска они не нужны. Пользовательские порты ограничены 16 значениями; при внешнем сравнении автоматически добавляются локальные 443 и 22. Общий лимит времени — 20–180 секунд. Результаты `--json` сохраняют прежние поля и добавляют `schema_version: 2`, `analysis`, `stages`, `settings`, `errors` и историю повторных попыток.

## Зависимости и намеренные ограничения

Используются существующие **Python 3 + ssl**, Linux sockets, `ip`, утилиты iptables и `nslookup` для внешних API. Права root нужны для SO_MARK, привязки к интерфейсу, raw ICMP/SYN и временных исключений. `curl`, `jq`, Nmap и MTR не обязательны; пакеты автоматически не устанавливаются. Для SYN используются существующий код TCP-пакетов и raw sockets. MTR не запускается без надёжного механизма обхода пользовательского перенаправления: промежуточные потери не используются как доказательство недоступности VPS.

IKE/500, NAT-T/4500 и WireGuard/51820 без конфигурации могут штатно игнорировать неизвестного клиента. Общая UDP-строка не является полезной проверкой этих протоколов. ACK/FIN/NULL/Xmas не улучшают уверенность в бане адреса достаточно, чтобы добавлять нагрузку и новые неоднозначные статусы. Пробы с выдуманным SNI, массовое сканирование, постоянный захват трафика и изменения пользовательских VPN не выполняются.

Check-Host использует [официальный API](https://check-host.net/about/api?lang=en): запуск асинхронной проверки, `request_id`, polling результатов, обработку незавершённых `null`. Для сильного сравнения учитываются совпадающие IP/порт и независимые страны/ASN; ошибка API не становится сетевым результатом VPS.

## Проверка реализации

Автоматические сценарии: `tests/server_diagnostics.py` и `tests/server_extensions.py`. Они покрывают сетевые ответы, loopback-сокеты, ASN/RPKI, некорректные пакеты, отрицания firewall, неполные снимки цепочек, таймауты, отмену и итоговую классификацию.

Полный запуск на Linux с BusyBox и Python 3:

```sh
sudo python3 tests/run_checks.py
```

На Entware выполнены 89 основных и 44 дополнительных теста VPS, 67 тестов DNS, проверки сайта, shell-регрессии и ввод в настоящем PTY. Проверены обычный и прямой HTTP GET, WAN-интерфейс и удаление временных правил. На контрольном VPS получены ответы TCP 22/80/443, SSH и TLS 1.2/1.3; молчание 8080/8443 не привело к заявлению о полном бане IP.

Внешние API могут быть недоступны из конкретной сети. При живой проверке Check-Host и InternetDB не всегда проходили TLS; Globalping возвращал результаты. Ошибки API показаны отдельно. Искусственная блокировка провайдером не создавалась; соответствующие случаи классификации проверяются моделируемыми ответами.

У Globalping задания опрашиваются общим циклом с единым сроком. Принимаются только результаты для совпадающего `resolvedAddress`. Семантика TCP сверена с [реализацией TCP ping](https://github.com/jsdelivr/globalping-probe/blob/master/src/command/handlers/ping/tcp-ping.ts): учитывается установленное соединение.
